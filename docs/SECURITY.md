# Security and privacy

This document separates current guarantees from proposed hardening. A statement
in the hardening backlog is not implemented merely because it is documented.

## Threat model

isaacli is a local CLI running with the user's privileges. Its sandbox limits
commands generated by the model; it is not a boundary against the user, root,
malware already running as the user, a compromised Python process or an
unlocked desktop session.

The current design aims to prevent accidental Git publication, obvious
credential logging, workspace escape and access by ordinary local users where
explicit restrictive modes are applied. It does not provide application-level
encryption at rest. Disk encryption, backup policy and operating-system account
security remain part of the protection model.

## Data stored locally

| Data | Current location | Current protection and contents |
| --- | --- | --- |
| Configuration | `~/.config/isaacli/config.json` or `XDG_CONFIG_HOME` | Atomically written with mode `0600`; contains profiles, endpoints, credential identifiers and permissions, not API-key values |
| API keys | Adjacent `secrets.json` | Plain JSON, atomically written with mode `0600`; no application-level encryption or OS keyring yet |
| Sessions | `tool_harness/cli_sessions/*.jsonl` | Plain JSONL; contains prompts, answers, commands, tool arguments/results, paths, errors and bounded diffs returned by file mutations; directory/file modes currently follow the process umask |
| Feedback | `tool_harness/feedback/*.jsonl` | Plain JSONL; may include the last answer and session metrics; modes currently follow the process umask |
| Runtime coordination | `XDG_RUNTIME_DIR/isaacli` or `/tmp/isaacli-<uid>` | Process identities and managed-Ollama state, not conversation content; the application requests a `0700` directory |
| Ollama models | Ollama-managed paths | Model weights and Ollama data; outside isaacli's secret store |

Git ignores sessions, feedback and secrets, but `.gitignore` is not access
control, encryption or a backup exclusion. Copying the clone can copy ignored
conversation files. Tests that construct sessions must redirect all private
state to temporary directories rather than relying only on an isolated config.
Mutation diffs are capped before entering the model conversation and session
log, but they can still repeat sensitive file content. They therefore have the
same private-data status as prompts and tool arguments, not a weaker telemetry
classification.

## API keys

Profiles store a credential identifier and load the corresponding value from
`secrets.json` only when constructing a remote provider. The key is held in the
Python process and sent as an `Authorization: Bearer` header to the configured
OpenAI-compatible endpoint. It is intentionally absent from config and session
events, and setup/runtime error formatting redacts common `api_key=...` forms.

Mode `0600` is meaningful protection against other ordinary local accounts, but
the value is still plaintext to the owning user, root, same-user malware and
backups. Pattern-based redaction also cannot guarantee removal if a remote
server reflects the literal key without a recognisable label. Never pass keys in
prompts, command lines, tool arguments or URLs.

The preferred future design is the operating-system keyring (Secret Service /
GNOME Keyring on Linux), with a clearly disclosed `0600` file fallback. File
encryption with a key stored beside the ciphertext would add complexity without
adding a security boundary. Any encrypted fallback must use a reviewed AEAD
construction and obtain its key from the OS keyring or a user secret derived
with a password-hardening KDF; do not invent a cryptographic format.

## Conversations and remote providers

Local Ollama keeps model requests on the machine. Selecting a remote provider
sends the system prompt, conversation history, relevant tool schemas and later
turn context to the configured endpoint. Tool execution still happens locally,
but tool results included in the conversation can be sent on the next model
request. Users must treat the remote provider's privacy and retention policy as
part of their own threat model.

Session logs intentionally support resume and therefore contain substantially
more sensitive material than metrics. They are not currently encrypted. On a
multi-user machine, shared checkout or synchronised/unencrypted backup, users
should treat the session and feedback directories as private records and purge
or protect them accordingly.

## Removal and recovery

`uninstall` preserves all private data. `uninstall --purge` deletes config,
secrets, sessions, feedback and stale runtime state after confirmation.
`uninstall --purge --ollama` additionally removes a recognised official Ollama
layout. The clone is always preserved. See [INSTALLATION.md](INSTALLATION.md)
for exact ownership checks, partial-failure behaviour and isolated validation.

Deletion is filesystem deletion, not guaranteed secure erasure: copy-on-write
filesystems, SSD wear levelling, snapshots and backups may retain prior blocks.
Use encrypted storage and manage snapshots/backups when that distinction
matters.

## Hardening backlog — not current guarantees

The most useful next changes, in order, are:

1. Move sessions and feedback to `XDG_STATE_HOME/isaacli`, migrate legacy data,
   and enforce `0700` directories plus `0600` files.
2. Redirect config, sessions, feedback and runtime state in every test so tests
   never create private-looking artifacts in the real checkout or HOME.
3. Store API keys in the OS keyring with an explicit, tested file fallback.
4. Add retention controls and a user-visible option not to persist conversation
   content.
5. Redact exact known secret values before recording provider errors, commands
   and tool results, in addition to pattern-based sanitisation.
6. Consider optional AEAD encryption for sessions only after defining key
   recovery, export, resume, search, migration and data-loss behaviour.

These items improve privacy but are not all emergency fixes for a single-user,
full-disk-encrypted workstation. The file-mode/state-location work is the
highest-value prerequisite before adding cryptographic complexity.

## Contributor invariants

- Never place API-key values in config, session events, feedback, terminal
  output or test fixtures that could be mistaken for real credentials.
- Treat prompts, answers, commands, tool results, paths and feedback as private
  data even when Git ignores them.
- Keep remote-provider payload disclosure explicit in user documentation.
- Test permissions and redaction by inspecting files/effects, not only success
  messages.
- Do not claim encryption, secure erasure or complete custom-model cleanup when
  the implementation cannot provide it.
